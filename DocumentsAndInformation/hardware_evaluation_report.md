# TRIO2026 專案：工控與嵌入式硬體效能評估報告 (4C/4T vs 6C/12T)

本評估報告旨在針對 TRIO2026 分子診斷平台（基於 Windows 11 IoT Enterprise 平台與 WPF (.NET 8) 軟體架構），分析在 **4C/4T (4核心/4執行緒)** 與 **6C/12T (6核心/12執行緒)** 兩種不同 CPU 硬體規格下的系統表現、底層通訊驅動穩定度、條碼掃描器整合效能及整機 BOM 成本費用。

## 2. 評估背景與系統架構特性
TRIO2026 是一個典型的**精密工控與醫療檢測設備控制軟體**，其運作時具有以下高度併發且注重即時性的軟硬體特性：
- **WPF 前端介面**：WPF 的 UI 執行緒（Dispatcher Thread）為**單執行緒**運作，高頻動畫（如 Splash 載入動畫、Spinner）對 CPU 排隊極度敏感。
- **後台硬體控制與通訊**：高頻監聽或 Polling 多組硬體埠（如紫外線消毒控制 `UvHardwareService`、馬達、溫控、感測器、條碼掃描器等），通訊多採 Serial Port (RS-232/485) 或 USB (VCP/HID)。
- **資料庫讀寫 I/O**：使用 SQLite (`system_config.db` / `event_log.db`) 進行頻繁的系統設定與事件日誌併發寫入。

## 3. CPU 規格對比：4C/4T vs 6C/12T 效能表現

### A. 4C/4T 系統 (剛好夠用，但容錯率極低)
* **代表處理器**：Intel Celeron J6412、Pentium、Atom X 系列（工控主板常見 SoC）。
* **執行緒調度**：無超執行緒技術（Hyper-Threading），僅有 4 個實體核心處理所有 Windows 後台服務、WPF UI 與多路硬體通訊。
* **潛在風險**：當系統處於高負載階段（如設備啟動自檢、大容量日誌寫入、UI 連續動畫渲染），CPU 佔用率極易瞬間飆高，導致通訊中斷（Timeout）或 UI 卡頓。

### B. 6C/12T 系統 (高穩定度、高容錯之工業/醫療標準)
* **代表處理器**：Intel Core i5-1145G7E / Core i5-12450H 等嵌入式中高階處理器。
* **執行緒調度**：具備 12 個邏輯執行緒，作業系統調度空間極大。
* **系統優勢**：能將「UI 執行緒」、「硬體 Polling」與「資料庫 I/O」在實體核心上徹底分流，通訊抖動（Jitter）降至最低，維持 24/7 長期運行的絕對穩定。

## 4. 底層驅動與通訊速度評估 (以 Barcode Scanner 為例)

條碼掃描器（Barcode Scanner）常用於檢體管、試劑卡匣與操作員識別證的掃描，其通訊整合模式與硬體規格的關聯如下：

### A. USB HID 鍵盤模擬模式 (Keyboard Emulation)
- **運作機制**：將條碼字元模擬成鍵盤打字快速送入聚焦的輸入框。
- > [!WARNING]
  > **4C/4T 下的掉字風險**
  > 
  > 鍵盤模式極度依賴 WPF 主執行緒。當 4C/4T CPU 忙於其他工作時，WPF 的 UI 執行緒會來不及響應鍵盤事件，導致條碼字元丟失（例如 `12345678` 讀成 `123568`），在醫療設備中這屬於**高風險醫療事故**。
- **6C/12T 下的表現**：UI 執行緒時間片充足，基本不會掉字，但仍存在輸入焦點被點走而輸入失敗的 UX 瑕疵。

### B. USB 虛擬序列埠模式 (Virtual COM Port, VCP) ⭐ 最推薦
- **運作機制**：掃描器被識別為 COM Port，WPF 背景執行緒以異步波特率（如 115200 bps）持續監聽。
- **4C/4T 下的表現**：需要分配一個獨立背景執行緒。當多路 COM 埠（PLC、感測器、條碼）同時 Polling 時，CPU 調度壓力極大，容易產生 200ms 以上的解碼延遲。
- **6C/12T 下的表現**：OS 可以指派專屬邏輯核心負責條碼監聽，**不論畫面焦點在哪，甚至在彈窗遮擋下，都能 100% 正確解析且反應在毫秒級**。

## 6. 隱藏之非金錢成本與售後維護費用
- **散熱風扇與維修率**：
  - **4C/4T**：通常為 **無風扇 (Fanless)**。沒有風扇壞掉、吸入灰塵老化、或產生軸承噪音的問題，**售後出保與維護率極低**。
  - **6C/12T**：通常需要風扇散熱。風扇壽命通常為 3~5 年，在醫療診斷環境中，需要定期進行風扇更換與防塵維護，會產生**定期的維護人力成本**。
- **軟體開發與 Debug 研發成本**：
  - **4C/4T**：為了預防通訊超時、掉字、UI 阻塞，軟體團隊必須耗費**數十甚至數百小時**進行極致的非同步 (Async/Await) 程式碼優化、執行緒鎖定調校與壓力測試。**這段研發人力成本往往遠高於硬體價差**。
  - **6C/12T**：硬體效能餘裕充足，軟體開發容錯率高，可大幅縮短產品的上市時間。

## 7. 結論與商業決策配置建議

> [!TIP]
> **建議一：高單價醫療診斷/精密分析設備 ➡️ 首選 6C/12T 方案**
> 
> 如果您的設備屬於低產量、高單價（如醫療檢測儀器），建議不要省下這約 **12,000 元台幣** 的硬體價差。相較於整機高昂的售價，條碼讀取的 100% 準確率、通訊零丟包、以及順暢不卡死的 UI 體驗能大幅降低未來因軟硬體衝突產生的售後維護與出保固費用。

> [!NOTE]
> **建議二：大量出貨之低單價工控 Kiosk/控制盒 ➡️ 採用 4C/4T 方案**
> 
> 如果產品面臨極大的市場價格競爭且出貨量達數千台，則採用 4C/4T 方案以省下數十萬元的採購費與授權費。但必須確保軟體團隊在開發時：
> 1. 條碼全面配置為 **VCP 虛擬串口監聽**（徹底避免鍵盤模擬模式）。
> 2. 將硬體通訊執行緒優先權提升，且 100% 採用非同步 I/O，精簡 WPF 介面複雜陰影與高頻動畫，確保核心運算效率。
